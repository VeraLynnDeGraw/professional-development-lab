# CODEMATE

A human-controlled AI developer assistant for understanding, planning, implementing, reviewing, testing, and documenting software changes.

CODEMATE is being developed as part of the **Professional Development Lab**, a professional software engineering portfolio focused on practical AI systems, reusable architecture, disciplined AI-assisted development, and human-controlled automation.

## Purpose

CODEMATE is designed to help developers work with software projects while keeping the developer in control of consequential actions.

The system is intended to:

* inspect project structure
* explain code and architecture
* create implementation plans
* propose code changes
* review proposed or existing code
* plan and interpret tests
* assist with documentation

CODEMATE is designed as a **developer assistant**, not an autonomous replacement for the developer.

## Evidence Model

CODEMATE explicitly separates information according to its evidentiary status.

```text
OBSERVED
INFERRED
PROPOSED
UNKNOWN
```

### OBSERVED

Information directly discovered from the project, filesystem, tools, or executed operations.

### INFERRED

A conclusion derived from observed information.

### PROPOSED

A change, plan, or recommendation generated by CODEMATE that has not yet been approved.

### UNKNOWN

Information that CODEMATE does not currently have enough evidence to determine.

CODEMATE should never present an inference, proposal, or assumption as an observed fact.

# Workspace Masking

CODEMATE operates on a **masked workspace by default**.

Machine-generated files, dependencies, caches, build artifacts, repository metadata, and potentially sensitive environment files should not automatically become part of CODEMATE's working context.

The purpose of workspace masking is to:

* reduce unnecessary context and token usage
* improve signal-to-noise ratio
* reduce accidental exposure of sensitive information
* prevent generated artifacts from being mistaken for source code
* create a predictable inspection boundary

Masking is **non-destructive**.

CODEMATE does not delete, modify, or move masked files.

Instead, the files remain on disk while being excluded from the default project context.

### Current Default Exclusions

```text
.git/
.venv/
venv/
__pycache__/
.pytest_cache/
*.egg-info/
```

The masking architecture is intended to expand to additional generated, dependency, build, and environment patterns such as:

```text
node_modules/
build/
dist/
coverage/
.env*
```

Future versions may provide controlled mechanisms for explicitly requesting normally masked content.

# Alpha.2 Architecture

The current implementation follows a deliberately small boundary:

```text
Human
  ↓
CODEMATE CLI
  ↓
inspect_project()
  ↓
ProjectContext
  ↓
Human-readable output
```

The CLI is responsible for communicating with the developer.

The project inspection module is responsible for filesystem inspection.

This separation prevents the CLI from becoming the inspection engine and gives future CODEMATE capabilities a reusable project-context foundation.

---

# Alpha.2 Capabilities

The current implementation can:

* inspect a project directory
* resolve the project's absolute root
* discover meaningful project files
* record file sizes
* exclude known generated/environment artifacts
* reject invalid project paths
* expose inspection through the `codemate inspect` command
* report evidence states
* operate without a paid AI service

The current implementation does **not**:

* call an AI model
* modify project files
* execute arbitrary shell commands
* install dependencies
* modify Git history
* push to GitHub
* make production changes

These boundaries are intentional.

# Engineering Principles

## Human-in-the-Loop

CODEMATE proposes consequential actions rather than silently performing them.

The developer maintains final authority.

## Workspace Safety

CODEMATE starts from a masked workspace rather than assuming every file should become AI context.

## Transparency

CODEMATE distinguishes observed information from inference, proposals, and unknowns.

## Modularity

Capabilities should remain separated into small, understandable, testable components.

## Testability

Implementation should be accompanied by explicit validation.

## Local First

The system prioritizes free and local execution before introducing paid services or external infrastructure.

## Provider Independence

Future AI functionality should be separated behind a provider boundary so that CODEMATE is not permanently coupled to one model or service.

## Minimal Architecture

CODEMATE should introduce complexity only when a real requirement justifies it.

# Safety Boundaries

CODEMATE Alpha does not provide:

* autonomous destructive actions
* unrestricted shell execution
* automatic GitHub publishing
* arbitrary dependency installation
* unsupervised file modification
* automatic production changes

Future capabilities that can modify the user's environment must provide an explicit human approval boundary.

Consequential actions should communicate:

```text
WHAT
WHY
WHERE
RISK
```

before approval.

# Alpha Development Philosophy

CODEMATE is itself an experiment in disciplined AI-assisted software engineering.

The project is intentionally being developed in small increments so that each milestone can be:

1. understood
2. implemented
3. tested
4. reviewed
5. documented
6. committed
7. released

The goal is not simply to create an AI coding tool.

The goal is to create a developer assistant whose behavior, boundaries, evidence, and changes can be understood by the human using it.
